# 国内更新发布

自动更新使用两条第三方 GitHub 镜像读取本仓库 `updates/latest.json` 和发行附件，并保留 GitHub 作为备用。镜像只是转发服务，可能限速、失效或无法在某些网络中使用；用户请求会经过对应镜像。若以后需要更稳定的国内分发，应迁移到自行控制的国内对象存储或 CDN。

## 签名密钥

`update-channel.json` 保存更新清单验证公钥和清单地址，必须随程序打包。签名私钥在项目仓库外的当前用户目录 `.tangli-release-signing/update-ed25519.pem`；禁止提交、分享或上传私钥，请将其安全备份。私钥丢失后，已安装的程序无法验证新密钥签署的国内清单，必须先让用户手动更新包含新公钥的程序。

Windows 的文件夹可能继承宽松权限。生成或恢复密钥后，检查密钥文件及其所在文件夹的 ACL，确保只有发布者、SYSTEM 和管理员可访问；不要放在公共共享目录。

## 发布新版本

以版本 `1.2.0` 为例（实际发布时使用新的版本号）：

1. 修改版本号，运行测试，构建 EXE，并准备 `Tangli-v1.2.0-Windows-x64.exe`。发布前确认分支、代码和文件内容正确。
2. 用以下命令将 EXE 切分为 48 MiB 附件并生成签名清单；输出目录不能预先存在。替换版本号与各路径：

   ```powershell
   $bases = 'https://gh-proxy.com/https://github.com/devin2255/bitan-pond/releases/download/v1.2.0|https://ghproxy.net/https://github.com/devin2255/bitan-pond/releases/download/v1.2.0'
   node tools/prepare-domestic-update.cjs build 'dist/Tangli-v1.2.0-Windows-x64.exe' '1.2.0' $bases 'dist/domestic-v1.2.0' "$env:USERPROFILE/.tangli-release-signing/update-ed25519.pem"
   ```

   如需填写更新说明，在私钥路径后追加 UTF-8 文本文件路径。脚本会检查私钥与应用内公钥是否匹配，输出各分片和 `latest.json`。
3. 将 EXE 和全部 `.part-*` 文件上传到同版本的 GitHub Release，核对文件大小及 SHA-256，发布正式发行版。等附件公开可用后，才将生成的 `latest.json` 复制到仓库 `updates/latest.json` 并提交、推送到 `codex/boss-on-lotus`；否则用户可能提前发现无法下载的版本。
4. 在不使用代理的网络中检查两条清单地址及至少一条镜像的分片下载，完整下载、合并并验证 SHA-256。再检查 GitHub 源和镜像失效时的回退。第三方缓存可能导致最新清单延迟出现。

发行版体积较大，完整 EXE 和分片需要额外存储空间；不要删除仍需提供更新的发行附件。修改镜像地址或更换公钥需要先随新程序发布。
